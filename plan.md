# JP Infracon — Implementation & Design Plan

## Product objective and delivery boundary

Continue the supplied JP Infracon Android application from its existing Expo Router/React Native code and follow the Production-Ready PRD. The app must not be described as production-ready simply because the screens render: persisted business records, server-side access checks, traceable status changes, safe offline drafts, and honest empty/error states are the implementation standard.

The current increment adds a limited workforce foundation: site-scoped worker/technician/contact records with minimal personal data, separately authorised manual KYC status review, and effective-dated rate proposals/activation with prior-rate history and audit. Vendors, document handling, subcontract work measurements, attendance-to-payable computation, advances, and payroll remain open. No invented seed metrics or hardcoded business successes will be presented as real records.

The inventory increment now delivers an organisation-shared base-unit material catalogue, editable only with organisation-level catalogue authority, and an append-only site-scoped register for accepted inward receipts, consumption/issue, returns-to-store, wastage and damage. A different authorised reviewer posts or rejects submitted movements. Posted balances are derived server-side with exact thousandth-unit arithmetic; outbound posting locks the material row and is blocked if it would make stock negative. Idempotency keys, actor attribution and audit events are retained. The queue reports its exact total and returns up to the 200 oldest pending entries; recent history is limited to 100 posted/rejected entries and is not yet paginated or exportable. Purchase orders, supplier receipt documents, partial/rejected delivery quantities/evidence, material-request allocation, transfers, physical counts/variance approvals, adjustment/reversal workflows, low-stock notifications and full history pagination/export remain incomplete.

The supplied Expo source is the accepted working baseline. The account screen creates real organization/site-scoped users, reveals a random temporary password only once, supports audited role-checked membership changes, restricts global password reset to Super Admin, and requires authority over every target role in the organization for role assignment or management: Super Admin/Owner can assign the eligible business roles (not create another Owner through this screen); Directors can assign Contractor/Admin and site roles; Contractor/Admin can assign site-scoped roles only. Do not seed named users; Sameer Swain and Sipun remain user-provided examples, and named accounts must be explicitly created through the secure UI.

### Next bounded increment — petty-cash movement ledger

Add site-scoped funds with a named active site custodian, integer-paise authorised limit, reconciliation period, creator and auditable custodian acknowledgement; an authorised finance/admin user creates the fund, and it is not available for movements until the named custodian acknowledges it. Capture separate funding, cash-expense and cash-return movements with date, amount, category, payee/returner, payment mode, actual payer, source account, purpose, optional same-site task allocation, receipt reference or a reason when a receipt is unavailable, and creator. Draft → Submitted → Approved/Rejected → Cancelled/Posted transitions use distinct-person review/post, required reasons, idempotent mutations, append-only audit and transactional fund-row locks. A balance is derived only from Posted funding and cash returns minus Posted expenses; no direct balance override is permitted, and posting revalidates both available cash and the fund limit. This slice records internal ledger events only and does not execute or verify bank/UPI transactions. Reconciliation/variance adjustments, private receipt-file upload/download, supervisor reimbursement liabilities, advances/retentions/notes, and full finance policy/offline/export work remain separate outcomes; personal outlays never reduce site petty cash.

## Implementation approach

- Keep the fixed Expo Router / React Native / TypeScript / NativeWind starter, managed tRPC/Express API, and MySQL-compatible Drizzle database. Keep the fixed Metro/API ports (8081/3000).
- Authenticate individual users by username/password with salted server-side password hashes, persistent server-session revocation, and no public SSO or self-registration. Keep global Super Admin separate from business roles; active membership, project/site assignments and grants remain server-resolved for every protected operation. Do not add a universal developer account, client-side privileged role toggle, or local-only authorization.
- Extend `drizzle/schema.ts` with normalized organisation, membership, project, site, scoped permission, worker profiles/site assignments, effective-dated engagement/rate reviews, daily report/item, attendance, material request/item, material catalogue, stock movement, idempotency and append-only audit records. Keep business status and computed ledger values server-controlled; avoid JSON blobs for core records. Keep historical creator attribution nullable where its original value was never recorded.
- Add feature-oriented backend procedures with schema validation, site-scope enforcement, permission checks, legal status transitions, actor/timestamps, reason capture and idempotent mutations. Schedule rescheduling recomputes its impact under row locks; inventory posting serializes per-item balance checks and derives stock only from Posted movement rows. The server, not the client, selects final status and balance. Use transactions when changing multiple related records. Keep database access behind server-only modules. The current managed MySQL-compatible database does not expose CHECK constraints in its installed schema; enforce rate positivity, effective-date ordering, positive quantities, and nonnegative stock at the server boundary, and do not claim those checks are database-enforced.
- Connect the field screens to typed tRPC queries/mutations. Show real persisted records and honest loading, empty, denied, offline and retry states; remove hardcoded names, dates, totals and fabricated approvals from production paths. Client-side local drafts use AsyncStorage only for explicitly offline-capable drafts, each with a UUID idempotency key and visible Local Draft/Pending Sync/Synced/Conflict/Sync Failed state. Never present a pending action as approved or posted.
- Keep private evidence indexed in the database and store bytes via the managed object-storage flow only after server-side authorization; do not expose public file links or upload service credentials to the client.
- Preserve portrait-first, one-handed screen design, readable outdoor contrast, accessible touch targets and the existing JP teal/graphite/amber system. English remains the first interface language with a string-resource seam for Hindi and Odia.
- The present increments do not claim the entire PRD. Vendor/subcontract-measurement extensions, inventory transfers/physical counts/full procurement, supplier-payment exceptions/advances and worker-payable/petty-cash/reimbursement workflows, schedule work calendars/resource conflict resolution/approval, safety close-out, exports, push delivery, backup/restore exercises, Android device verification, and signed Android release artifacts remain incomplete until implemented and evidenced.

- `components/jp/`: existing reusable field-log UI primitives.
- `lib/jp/domain.ts`, `lib/jp/scheduling.ts`: shared presentation/domain types and pure date/dependency impact calculations; no privileged policy decisions.
- `lib/jp/local-repository.ts`: durable local-only offline drafts and sync metadata; never a source of server approval or official totals.
- `lib/trpc.ts`: typed mobile client to the managed API, using runtime-provided API base URL and secure native session credentials.
- `components/jp/auth-gate.tsx`, `server/_core/credential-auth.ts`, `server/jp/accounts.ts`, `lib/jp/account-role-policy.ts`, and `drizzle/schema.ts`: username/password entry, one-time Super Admin bootstrap, password-hash verification, persistent login throttling and revocable sessions, plus audited organization/site account administration; Super Admin recovery and role/site reassignment remain open.
- `server/routers.ts`, `server/jp/`: protected, validated JP business procedures, including task, workforce, inventory, and incremental finance modules, plus site-scope/permission logic; `server/db.ts` is the database boundary.
- `drizzle/schema.ts`, `drizzle/000*.sql`, `drizzle/meta/`: normalized records and additive migration history for the shared managed MySQL database.
- `tests/`: pure domain, permission and workflow unit/API tests; avoid destructive testing writes against the shared production database.
- `plan.md` and `TODO.md`: implementation decisions and outcome-based progress/open acceptance clauses.

## Design direction

### Three candidate movements

- **Industrial Field Ledger** — 0.07 probability: rugged site-log visual language with graphite, safety amber, and clear ledger rows.
- **Civic Utility Calm** — 0.06 probability: quiet civic-service interface with cool paper surfaces, teal action color, and measured density.
- **Monsoon Signal** — 0.04 probability: deep indigo base with rain-teal highlights and high-contrast alert moments.

### Selected: Industrial Field Ledger

**Design Movement:** Industrial field-logbook meets contemporary operations control room: functional, tactile, and calm under pressure.

**Core Principles:** Evidence before decoration; one clear next action per screen; status is always visible; density is earned by operational relevance.

**Color Philosophy:** Charcoal and warm paper create a current site-register feeling without nostalgia. Safety amber is reserved for attention and risk, teal marks actions and verified/synced information, and red denotes blocking/error states. Maintain outdoor contrast and low-light legibility.

**Layout Paradigm:** A vertical field log rather than a centred card dashboard. The app bar carries identity and connection state; content flows from a short operational brief into stacked site/action records. Avoid unnecessary horizontal scrolling.

**Signature Elements:** A thin amber field-line on important cards; monospaced micro-labels for IDs/times/sync metadata; compact status pills with a dot and plain-language state.

**Interaction Philosophy:** Every tappable record exposes its state and next step. Primary actions have comfortable targets; forms progress draft → review → submit. High-impact actions explain confirmation and reason requirements; offline actions show exactly what is queued.

**Animation:** Restrained 150–220ms transitions and a subtle active-sync pulse; avoid decorative motion and motion that obscures status.

**Typography System:** System sans for headings/body with clear weight contrast; small monospaced styles for IDs, timestamps and sync metadata; compact sentence-case headings and short operational labels.

**Brand Essence:** The field-operations ledger for JP Infracon teams who need to move work forward with traceable evidence. Personality: grounded, decisive, accountable.

**Brand Voice:** Direct and situational. Example lines: “Keep today’s work moving.” and “Save draft — submit when the signal is back.”

**Wordmark & Logo:** Preserve the supplied compact JP monogram built from offset structural beams inside a square safety marker; negative space suggests a forward arrow without implying approval.

**Signature Brand Color:** `#0F766E`, a deep construction teal for primary actions and verified/synced signals.

## Build and delivery workflow

Use the initialized managed Mobile project and its fixed Expo starter. Run the starter database preparation once before initial API traffic, use registered TypeScript diagnostics, then run focused tests/typecheck and restore Metro/API listeners only when needed. Do not run Android/EAS release builds inside the Sandbox. An APK/AAB is a deliverable only after an actual Dashboard build succeeds; do not claim signing or production readiness without that evidence. Any Android SDK/OS support range must be documented before release QA. Database writes during tests affect the same managed database used by production, so validate through pure tests and code inspection unless a safe isolated database is available.
